## Фаза 2, дополнение — CSG даёт мусорную геометрию

CSG-булевы операции на выходе дают избыточные треугольники, T-вершины
и несваренные вершины. Без чистки в оболочке легко получить 2 млн
треугольников там, где хватит 80 тысяч.

```
После каждой булевой операции прогоняй меш через постобработку:

1. BufferGeometryUtils.mergeVertices() с эпсилон 1e-4 — сварка вершин
2. удали вырожденные треугольники (площадь < 1e-8)
3. пересчитай нормали: computeVertexNormals(), но с порогом угла —
   рёбра кладки должны остаться острыми, цилиндр — гладким
4. выведи в консоль: треугольников до / после

Целевая цифра для оболочки башни: не больше 150k треугольников.
Если CSG выдаёт больше — уменьшай сегментацию цилиндра, а не терпи.
Радиальных сегментов 96 хватает за глаза: при радиусе 8 м это грань
шириной 0.5 м, глаз не различит.

Если после чистки всё равно тяжело — предложи альтернативу CSG:
собрать оболочку из lathe-геометрии профиля + отдельные меши проёмов,
без булевых операций вообще. Обоснуй, что выбрал.
```

## Фаза 4 и 6, дополнение — коллайдеры отдельно от визуала

Самая дорогая ошибка в проекте. Trimesh-коллайдер по CSG-мешу башни
убьёт физику: rapier будет считать пересечения по сотне тысяч треугольников
каждый кадр.

```
Правило: визуальная геометрия и коллизионная — РАЗНЫЕ меши.

Коллайдеры собирай из примитивов, а не из визуального меша:
- стена башни — набор box-коллайдеров по окружности (24-32 штуки на ярус),
  или cylinder-коллайдер снаружи + внутренний как "полый" через
  несколько сегментов
- пол яруса — cylinder-коллайдер с вырезом под окулюс,
  собранный из кольцевых сегментов
- лестница — НЕ отдельный коллайдер на каждую ступень.
  Один наклонный box-коллайдер вдоль марша (пандус) + autostep в rapier,
  чтобы визуально персонаж шёл по ступеням, а физически — по рампе.
  300 коллайдеров ступеней это гарантированные просадки на мобильном.
- проёмы окон — не нужны коллайдеры вообще, если игрок в них не пролезает;
  проверь габарит капсулы против innerWidth окна

Отладочный режим: клавиша F4 показывает wireframe всех коллайдеров
поверх визуала. Мне нужно видеть расхождение.
```

## Фаза 7, дополнение — процедурный шейдер не должен считаться каждый кадр

Полосатость кладки и ромбовидный normal map по noise в фрагментном
шейдере — это красиво в редакторе и дорого на телефоне.

```
Процедурный шейдер используем как ГЕНЕРАТОР текстур, а не как рантайм-шейдер.

1. Сгенерируй полосы, ромбы и вариацию цвета один раз при сборке
   (или один раз при первом запуске) в offscreen-рендер
2. Запеки в тайлящиеся текстуры: albedo, normal, roughness, 1024x1024
3. Сохрани как KTX2/Basis (не PNG и не JPG!) — сжатые GPU-текстуры,
   распаковка не нужна, память в разы меньше
4. В рантайме — обычный MeshStandardMaterial с этими картами
   и триплanar-наложением, чтобы не мучиться с UV на CSG-геометрии

Материалов на всю башню должно быть 3-4, не больше:
камень наружный, камень внутренний, керамика труб, дерево/металл деталей.
Каждый лишний материал — это лишние draw call'ы.

Исключение: если хочешь настоящий процедурный шейдер ради вариативности —
покажи мне замер обоих вариантов на мобильном профиле, и решим.
```

## Фаза 8, дополнение — солнце это самая дорогая часть проекта

Динамический directionalLight с тенями по восьмиэтажной геометрии —
главный кандидат на срыв бюджета кадра. Плюс объёмный свет, который
я просил, на мобильном может стоить дороже всей остальной сцены.

```
Тени:

- НЕ обновляй shadow map каждый кадр. Солнце двигается только когда
  я двигаю скраббер времени. Ставь light.shadow.needsUpdate = true
  вручную при изменении даты/времени, в остальное время тень статична.
  Это буквально бесплатные 5-10 мс кадра.
- Тесный shadow frustum: не покрывай всю сцену одной картой.
  Ограничь камеру тени текущим ярусом ± 1.
- Разрешение карты: 2048 десктоп, 1024 мобильный, переключается
  автоматически по detectGPU.
- PCFSoftShadowMap на десктопе, обычный PCF на мобильном.

Объёмный свет (godrays):

- Реализуй ДВА варианта и переключай по производительности:
  (а) дешёвый: конус полупрозрачной геометрии от проёма внутрь,
      additive blending, мягкие края — почти бесплатно
  (б) дорогой: raymarching в постпроцессе — только десктоп,
      и только если бюджет кадра позволяет
- По умолчанию на мобильном — вариант (а). Не спрашивай, просто сделай так.

Детекция попадания луча в окно:

- Не raycast каждый кадр по всей геометрии. Считай аналитически:
  азимут и высота солнца из suncalc против азимута и раствора проёма —
  это чистая тригонометрия, микросекунды.
  Raycast только для подтверждения, и только когда аналитика говорит
  "должно попадать".
- Вынеси эту математику в src/lib/solar.ts и покрой тестами.
```

## Фаза 11, расширенная

Исходный текст фазы оставь, добавь к нему:

```
Дополнительно к тому, что уже написано:

1. Текстуры: все в KTX2/Basis через toktx или gltf-transform.
   Draco сжимает только геометрию — на текстуры он не влияет,
   а именно текстуры обычно съедают GPU-память на мобильном.
   Мипмапы обязательны.

2. Окклюзия по окулюсам. Внутри башни стены и купола закрывают почти
   всё. Frustum culling этого не ловит — он работает по камере, а не
   по стенам. Сделай портальную отсечку: игрок на ярусе N видит
   ярус N, ярус N+1 через окулюс, ярус N-1 через окулюс. Всё остальное
   не рендерится вообще. Это самая большая победа в этом проекте,
   потенциально 60-70% draw call'ов.

3. Адаптивный pixel ratio. Не рендерь в devicePixelRatio 3 на телефоне.
   Ограничь Math.min(devicePixelRatio, 2), и добавь динамическое
   понижение: если кадр стабильно > 33 мс, снижай масштаб рендера
   до 0.75, потом до 0.6. drei умеет через AdaptiveDpr.

4. three-mesh-bvh на всю статическую геометрию — ускоряет raycast
   для хотспотов, детекции луча и выбора объектов на порядок.

5. Инстансинг: ступени, блоки кладки, сегменты керамических труб,
   выступы на фасаде (30 + 31 штука). Всё, что повторяется — InstancedMesh.

6. Прогрессивная загрузка по ярусам. Первый ярус и оболочка грузятся
   сразу, остальное — фоном, пока игрок ходит внизу. Игра должна стать
   играбельной раньше, чем догрузится всё.

7. Освобождение памяти: dispose() геометрий, материалов и текстур
   при смене сцены и при HMR. Иначе за час разработки браузер съест
   всю память.

8. Замер на реальном устройстве. Не на десктопном Chrome с эмуляцией.
   У меня есть телефон, я проверю сам — просто дай мне билд и скажи,
   какие цифры смотреть.
```
